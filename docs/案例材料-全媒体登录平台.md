# 全媒体登录平台 · AI 案例材料

> 用途：案例评审现场（5 分钟陈述 + 15 分钟演示 + 5 分钟答疑）
> 主体：全媒体登录平台（内部代号 CreatorHub），v1.1.0
> 提效测算口径：**日均进出 20 次**（已确认），单次 60 秒 → 10 秒。

---

## 零、一句话定位（开场第一句就用这句）

> 我们把自己岗位里最机械的一段——「跨 5 个平台、十几个账号反复登录和找入口」——交给 AI 做成了一个本地工具，
> 现在这件事从每次 1 分钟压到 10 秒，而且掉登录会提前被提醒，不用等到发布前才发现。

**关于「AI 员工」的口径说明（讲的时候要主动交代，避免被问倒）**

这个案例里的 AI 承担的是两个角色：

| 角色 | 干了什么 |
|---|---|
| 开发 + 运维 | 从需求描述到代码、测试、双平台打包、问题定位，全部由 AI 结对完成 |
| 交付出的「数字同事」 | 就是这台工具本身：它替人承担了登录、切号、找入口、盯登录态这些机械动作 |

**要明确说的边界**：AI 不参与内容创作，也不代为发布、不抓平台数据。它承接的是「进入后台之前的那段脏活」，
真正的内容判断和发布动作仍然是人在做。这样讲既符合事实，也不会被质疑夸大。

## 一、案例逻辑必要素（对应表格，可直接粘贴）

| 必备要素 | 内容 |
|---|---|
| **搭建初衷** | 一个人要同时运营抖音、小红书、微博、视频号、快手 5 个平台的十几个账号。每次开工都得在各平台后台之间反复登录、切号、翻书签找入口，时间大量耗在「进得去」上，而不是「做内容」上。希望有一个地方，所有账号一次登录、长期保持，打开就是可操作状态。 |
| **要解决的问题** | 四个具体痛点：① 多平台多账号反复扫码登录，抖音尤其一重启就掉；② 同一浏览器同平台只能登一个号，切号等于重新扫码；③ 发布与数据入口分散，每次重新找链接；④ 纯网页方案做不到账号隔离（同域 Cookie 共享），掉了还不自知。 |
| **职责** | 为每个平台、每个账号维护一份独立且可长期保持的登录态；把 5 个平台创作者中心的登录与入口聚合到一个本地桌面窗口；负责登录态静默巡检与掉登录提醒；管理账号清单（增删改、排序、导入导出）。 |
| **权限（能干什么、边界在哪）** | **能做**：隔离登录态、聚合入口、定时保活、状态巡检、账号清单管理、跨设备导入导出。**不做**：不代用户操作平台、不自动发布、不抓取平台数据；不读取/不记录/不导出 Cookie 值、密码、token；不调用平台内部接口；不绕过验证码与风控；不替用户自动重新登录；数据只存本机，不上传任何服务器。**不承诺**：登录态能维持多久最终由平台策略决定，工具只提供条件并尽早提醒。 |
| **原耗时** | 每轮开工需在 5 个平台、十几个账号之间逐一登录/切号/找入口，单次进出约 **1 分钟**；按日均 20 次进出测算，约 **20 分钟/天**、**约 7 小时/月**。另有隐性成本：掉登录往往在发布前才发现，一次返工 5~10 分钟。 |
| **提效多少** | 单次从 **60 秒降到 10 秒，提效 83%（效率约为原来 6 倍）**；按日均 20 次测算，**每天省约 17 分钟、每月省约 6.1 小时**。隐性收益：掉登录提前暴露，基本消除「临发前卡住」的返工。 |

### 提效数字的换算口径（口径已确认为**日均 20 次**，现场被追问时用）

```
省下的时间 = 操作次数 × 单次节省 50 秒 ÷ 3600
单次节省    = 60 秒 − 10 秒 = 50 秒
日均 20 次  → 0.28 小时/天（约 17 分钟）
月 22 个工作日 → 6.1 小时/月
```

### 【0:30–1:30】痛点 · 具体到一个场景

说一个特别具体的场景。

早上开工，五个平台挨个打开，十几个号挨个点一遍。总有两三个号，昨天还好好的，今天一打开就要扫码。

那就扫。一个号扫码加验证，慢的时候一分钟。三个号，三分钟。

然后我坐下来准备发东西，发现抖音那个主号，不知道什么时候掉了。**页面还在，网址都没变，中间就弹了个登录框。**

这个时候，稿子写好了，片子剪好了，就卡在发布这一步。

---

### 【1:30–2:00】为什么以前的办法都不行

这些办法我都试过。

浏览器开一堆标签页，不行。同一个平台只能登一个号，登第二个，第一个就被顶掉。

用多个浏览器，或者浏览器的多用户，能用，但每次要换窗口、重新找位置，而且它不会告诉我哪个号掉了。

做个网页把所有后台聚在一起，四个平台的创作者后台都不允许被别的网页嵌进去，这条路走不通。

---

### 【2:00–3:00】最后做成了什么（边说边指屏幕）

最后的办法，是做一个本地的小软件。

打开是这么一个界面：左边按平台分栏，每个账号一张卡片。

关键是，**每个账号的登录状态是分开存的**。同一个平台我登三个号，三个都在，谁也不顶谁。

卡片上会显示状态。正常的写「登录态正常」，掉了的会标出来，告诉我需要重新登录。

还有一点很重要：它会每隔几个小时，在后台悄悄把每个号访问一次，让平台那边的登录状态续着，不至于放着放着就凉了。

---

### 【3:00–4:00】这东西是谁做的

这个东西，代码我一行没写，是我和 AI 一起做出来的。

我做的是把需求说清楚：要几个平台、每个平台几个号、登录状态必须互不影响、要能撑一个月。然后让它给我几个方案，说清楚哪个方案真能做到账号隔离。方案定了，它写代码，我试用，有问题我截图给它。

中间有个问题挺典型。我发现明明掉登录了，界面还显示正常。我把截图发过去，它去查，最后定位到：那个页面网址根本没变，只是弹了个登录框，而原来的判断只看网址。后来改成连页面上的文字一起看，这个问题才解决。

包括最后的打包、Windows 和 Mac 两个安装包，也都是它做的。

算笔账。

以前每进出一次后台，从打开到能操作，大概一分钟。现在点一下卡片，十秒。

**提效 83%，效率是原来的六倍。**

但对我来说更值钱的，是另一件事：掉登录会提前告诉我，不用等到发布前才发现。这个返工，以前一个月总有两三次。

### 【4:40–5:00】边界与收尾

最后说清楚边界。

这个工具不碰平台任何接口，不存我的密码，数据只在我这台电脑上，也不会替我去发布任何东西。

它就是把我每天重复上百次的那个动作——登录、切号、找入口——拿走了。

而这个动作，恰恰是最不该由人来干的。

## 三、15 分钟演示脚本（讲「怎么搭、怎么用」）

### 3.1 演示前 3 个准备（提前做好，别在台上做）

1. 软件已打开，5 个平台账号卡片齐全、状态为「登录态正常」
2. 准备一个**空账号位**用于现场演示新建 + 登录
3. 准备一个「故意掉登录」的账号（提前清掉它的登录态），用于演示巡检识别

### 3.2 时间轴

| 时间 | 动作 | 要说的话 |
|---|---|---|
| 0:00–2:00 | 打开软件，展示全貌：按平台分栏、卡片、状态标识 | 「这是一屏，我每天的开场。以前这一屏要靠 5 个浏览器窗口拼出来。」 |
| 2:00–5:30 | **现场新建一个账号并登录** | 「新建 → 填别名 → 打开 → 扫码。注意这里：每个账号是一个独立分区，所以同平台第 3 个号登进去，前两个不会被顶掉。」 |
| 5:30–9:00 | **日常使用**：点卡直达后台，完成一次实际操作（发布/看数据），再从技术详情里开独立窗口并排 | 「入口聚合的价值就在这里：点一下就到位，不用再翻书签。」 |
| 9:00–12:00 | **巡检演示**：点「巡检登录态」，那个故意掉登录的账号被标成「疑似需要重新登录」 | 「关键点：它没有跳登录页、网址没变，页面里弹的是扫码浮层。我们靠读页面文字判断，所以能抓出来。」 |
| 12:00–13:30 | **导出/导入**：导出账号清单，展示导出文件里没有凭据 | 「换电脑靠这个迁移；但凭据不在里面，这是刻意的安全边界。」 |
| 13:30–15:00 | **收尾**：回到「从输入到产出」 | 「输入是一次点击，产出是完成一次发布——中间所有登录、切号、找入口的动作都被省掉了。」 |

### 3.3 「从输入到产出」现场怎么讲清

- **输入**：一次点击（选中账号卡片）
- **中间被省掉的动作**：打开浏览器、找书签、输入账号、扫码/等验证、切号、再找入口
- **产出**：在该账号的创作者后台里完成一次真实操作（发布一条内容 / 查看一次数据）

## 四、搭建过程：用了什么工具、关键提示词、工作流

### 4.1 工具与平台

| 项 | 内容 |
|---|---|
| 开发框架 | Electron（Node.js）+ 原生 WebContentsView，本地桌面应用，无需服务器 |
| 核心技术 | 会话分区隔离（每账号一个 `persist:` 独立持久化分区）、会话型 Cookie 加固（补远期有效期）、定期刷盘、定时静默巡检、页面内容判据 |
| 覆盖平台 | 抖音创作者中心、小红书创作服务平台、微博、微信视频号、快手 |
| 构建分发 | GitHub Actions 云端双平台打包（Windows NSIS/portable + macOS arm64/x64） |
| AI 协作方式 | 需求描述 → 方案取舍 → 代码生成 → 自动化测试 → 问题定位 → 打包发布，全程结对 |

### 4.2 关键提示词（可复用的骨架，换个场景照样能用）

1. **先把场景和硬约束讲死**
   > 做一个多平台创作者后台聚合工作台，覆盖抖音/小红书/微博/视频号/快手，每个平台至少 3 个账号，
   各账号登录态必须完全独立、互不顶号。

2. **把验收标准量化，并要求如实反馈**
   > 登录态要能保持一个月不掉线，支持 5 人以上同时使用。如果做不到，明确告诉我哪些条件做不到、为什么。

3. **先要方案取舍，再动手**
   > 先给我 2~3 个技术方案和取舍，说清楚哪个能真正做到账号隔离，我确认后再写代码。

4. **用现象描述 bug，不用术语**
   > 明明掉登录了，界面还显示登录态正常。我截图给你，你排查根因。

5. **改动必须可验证、可回溯**
   > 改完跑测试，列出改了哪几个文件、每处改动的理由，不要动其他逻辑。

### 4.3 工作流（从 0 到可分发，6 步）

1. **场景拆解**：列清平台、账号数、每天的真实操作路径，先算清时间花在哪
2. **路线选型**：对比网页聚合 vs 桌面应用，确认只有「每账号独立持久化分区」能真正隔离登录态
3. **数据层**：账号清单增删改查 + 排序 + 导入导出（只存别名/备注/网址，不存凭据）
4. **会话隔离与守护**：独立分区 → 会话 Cookie 补远期有效期 → 定期落盘 → 定时静默巡检 → 页面内容判据兜底
5. **界面与交互**：单窗口聚合入口，卡片式账号管理
6. **测试与分发**：自动化测试（数据层 + 会话守护）→ 云端双平台打包 → 分发给同事 → 按真实反馈迭代

### 4.4 使用工作流（这是「怎么用」那一栏要讲的）

> 首次按平台批量建卡并各登录一次（登录态写入独立分区，同平台多号互不顶号）→ 日常从卡片状态判断可用性，
> 点卡直达创作者后台完成发布与数据查看，需要对比时开独立窗口并排 → 开工前点一次「巡检登录态」，
> 软件常驻后台按 4~6 小时间隔静默保活 → 换机时导出账号清单再导入，各号重新登录一次即可。

## 五、哪里能改 / 同事怎么套用到自己工作里

### 5.1 这个工具哪里可以改（现场被问「能不能定制」时答）

| 想改什么 | 改哪里 | 难度 |
|---|---|---|
| 增加一个新平台 | 平台配置里加一条（登录入口、工作台地址、掉登录特征词） | 低 |
| 调整保活间隔 | 软件设置里直接调，最小 1 小时 | 无需改代码 |
| 调整掉登录识别灵敏度 | 平台配置里的「页面特征词」列表，加词即可 | 低 |
| 改界面配色 / 布局 | 样式文件 | 低 |
| 加字段（如账号分组、标签） | 数据层 + 卡片渲染 | 中 |

### 5.2 同事怎么套用（这段是推广的关键，讲的时候要给具体岗位）

**判断标准**：只要一个岗位满足「**多个系统 × 多个账号 × 反复登录 × 入口分散**」，这套做法就能直接搬。

可以举的岗位：

| 岗位 | 对应场景 | 迁移要点 |
|---|---|---|
| 多店运营 / 电商 | 淘宝、京东、拼多多、抖店多个店铺后台 | 换平台配置即可，逻辑完全一致 |
| 客服 / 社群运营 | 多平台工单后台、多个企微/公众号 | 同上，注意各平台的掉登录特征词不同 |
| 投放 / 广告优化 | 多账户广告后台（巨量、磁力、腾讯广告） | 账号隔离需求更强，收益更明显 |
| 财务 / 对账 | 多家银行、多个平台商户后台 | 建议单独一台设备，不与内容账号混用 |

**推广时的三句话**：

1. 你不需要会写代码，需要的是**把痛点和验收标准说清楚**——这是 AI 能接住的部分
2. 先做**一个平台、两个账号**跑通，再扩到全部平台，不要一上来做大而全
3. 一定要**先定边界**：哪些事绝对不做（不存凭据、不碰接口、不代操作），边界定死了，后面才不会跑偏

## 六、现场答疑预判（10 问，提前背下来）

| 可能被问 | 建议回答 |
|---|---|
| 这算不算绕过平台风控？ | 不算。它就是浏览器，只是把每个账号的浏览数据分开存放。不做验证码绕过、不改请求、不调内部接口。 |
| 账号密码存在哪里？ | 不存在工具里。登录态是平台自己发的会话凭据，存在本机对应账号的独立目录，工具不读取、不导出、不上传。 |
| 掉了会不会自动重登？ | 不会，也不打算做。自动重登需要存密码或接管验证，这两件事都越过了安全边界。工具只做「提醒你去扫一次码」。 |
| 换了电脑还能用吗？ | 能。导出账号清单（只有别名/备注/网址/排序），新机导入后每个号重新登录一次即可。 |
| 能自动发布吗？ | 不能。自动发布要调用平台发布接口，属于越界，也不符合平台规则。工具只负责让你「进得去」。 |
| 同事能直接用吗？ | 可以，已出 Windows 和 macOS 两套安装包，免安装版也有。首次打开需要按说明解除一次系统隔离标记。 |
| 为什么不用浏览器多用户/多开？ | 可以替代，但有两个硬伤：切换成本高（每次要换窗口+重新定位），以及**没有任何状态提醒**——掉了要自己发现。 |
| 维护成本高吗？ | 低。平台改版时最多改一处配置（登录特征词），不用动核心逻辑。日常零维护。 |
| 数据安全怎么保证？ | 全部本地存储，无服务器、无账号体系、无上传。导出文件里刻意不含任何凭据。 |
| 如果平台彻底改版怎么办？ | 最坏情况是该平台的掉登录识别暂时失效（会退回「无法判断」而不是误报正常）；登录和入口功能本身不受影响，因为那就是浏览器行为。 |

---

## 七、一句话收尾（陈述最后说）

> 它没有替我做内容，也没替我做判断。它只是把我每天重复上百次的那个「登录、切号、找入口」拿走了——
> 而这恰恰是最不该由人来干的部分。
